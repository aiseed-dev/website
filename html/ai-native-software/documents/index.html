2026.07.04 🌐 EN

文書で取り戻すのは、置き場ではない。原稿の持ち方だ。

門番(2-04)の内側に、最初に置く道具は文書である。ただし、この章の結論は「どの編集ソフトを立てるか」ではない。2026 年に入って、文書が住める場所が三つに増えたからだ。Office、自前の道具、そして Claude Docs である。三つとも便利で、三つとも鍵は他人か自分かのどちらかに寄っている。だから先に決めるのは、 原稿をどの形で持つかのほうだ。

Office は「使う」のではなく「通過させる」

Office から離れる理由を、まず誤解しないでほしい。これは効率化の話ではない。 30 分の作業が 30 秒になることは結果として起きるが、本質ではない。

事務処理を三つに分ける。

  • 入口 ── 他の人から届くファイル(Word、Excel、PDF)
  • 中身 ── 自分が考え、作業し、保存する場所
  • 出口 ── 他の人に渡すファイル(Word、Excel、PDF)

これまで多くの人は、三つとも Office で行ってきた。Word が来たら Word で開き、 Word のまま編集して、Word のまま返す。だが中身まで Office にしている限り、次の節で見るとおり AI は同僚にならない。

だから .docx・.xlsx・.pptx は、中身が住む場所ではなく、入口と出口で人とやり取りするための交換形式だと捉え直す。組織のルールは変えない。自分の中身の主導権だけ取り戻す。

Office の中では、AI は同僚にならない

なぜ中身を閉じた形式の外へ出すのか。Office の中にいる限り、AI は道具のままで、同僚にはならないからだ。

Word ファイルを AI に渡しても、毎回変換が起きる。.docx を解凍し、XML を読み、書式を剥がして、テキストを取り出す。Excel も同じで、セルの座標、書式情報、結合セル、シート間の参照が、AI と中身の間に挟まる。

結果として、AI は使えるが、同僚にはならない。「全文を読んで論点を整理して」と頼めてもレイアウトが崩れ、「この表を分析して」と頼めても結合セルや書式付きの値で混乱する。

中身を文字と構造化データに降ろした瞬間、この壁が消える。AI は直接読み、直接書き、考えを返す。編集の道具としての Office はそのまま残る。ただし中身は、 AI が触れる場所に保つ。

「処理する人」から「判断する人」へ

Office の中で事務処理をしている限り、自分は処理する人のままだ。Excel を集計する人、Word を整える人、数字を貼り直す人である。これらは AI で代替できる仕事であり、AI が安くなれば、組織はその役割から人を引き上げる。

中身を構造に降ろすと、役割が変わる。何をすべきかを考え、どう解釈するかを判断し、新しい仕組みを設計し、AI に何を頼むかを決める人になる。仕事の量ではなく、仕事の中身そのものが変わる。

処理する人は AI が代替する。判断する人は代替できない。中身を取り戻すことは、代替されない側に移ることだ。

具体例: 月次報告書 ── 同じ報告書、違う仕事

月次の売上報告書を作る作業で見る。

従来の流れ。Excel で売上データを開く。ピボットで集計する。グラフを作る。 Word に貼る。文章を書く。PDF にして上司に送る。このとき自分がしている仕事は、数字を整えることだ。

新しい流れ。裏のデータを読む。届いた .xlsx は機械が取り込む。集計を AI に書かせ、結果を表にする。グラフを組み込む。AI が文章を下書きする。自分が解釈と判断を書き加える。出口で .docx や PDF に変換する。このとき自分がしている仕事は、数字の意味を考えることだ。

「今月の前月比 +12% は、どの顧客の影響か。継続するのか。営業戦略を変えるべきか」。 Excel の中で集計操作をしている間は出てこなかった問いが、構造化された手元データと AI を前にすると立ち上がる。

原稿は文字で持ち、git に入れるのは原稿だけにする

ここがこの章の中心だ。決めることは二つしかない。

一つ目。原稿は AsciiDoc(.adoc)の文字で持つ。文字のファイルなので、git で差分が取れる。誰が、いつ、どの行を変えたかが残る。.docx は中身が圧縮された XML なので、差分が読めない。文字で持てば、AI がそのまま読み、そのまま書ける。

二つ目。git に入れるのは原稿だけにして、デザインは入れない。見た目を決めるテンプレートは、原稿とは別の置き場に持つ。同じ原稿に別のテンプレートを当てれば、別の体裁で出る。git の履歴に残るのは、中身が変わった差分だけになる。

原稿/            ← git に入れる。.adoc の文字だけ
  2026-09-事業報告.adoc
テンプレート/    ← git に入れない。見た目の決め
  houkoku.tmpl.adoc
出力/            ← git に入れない。刷った結果
  2026-09-事業報告.pdf

この決めから先が楽になる。原稿が文字なら、出口は選べる。PDF に刷る。.docx に書き出して相手に渡す。HTML にしてサイトに載せる。どれも同じ原稿から出る。

そして、adoc 形式でのデータ交換が、これから効いてくる。人と人のあいだも、人と AI のあいだも、やり取りする実体が文字になれば、途中で失われるものが無くなる。

様式の仕事は aiseed office ── ONLYOFFICE は日本語で合わない

原稿は文字でよい。だが、様式はそうはいかない。受け取った .docx の申請書を、決められた頁数、決められた行の位置、決められた列幅のまま開いて、直して、刷る。この仕事は、形式の互換そのものが中身である。

この用途で ONLYOFFICE は日本語の様式に合わない。だから aiseed office (aiseed-dev/officework)を作っている。 .docx と .xlsx を読み書きし、そのまま PDF にも刷るエンジンだ。

pip install officework

2026-09-20 に確かめた時点で、エンジンは 0.5.0 が PyPI に出ている(2026-09-04 公開)。ベータを外した版だ。役所が公開している PDF と、同じ字の行どうしを比べた数字が、公開の RELEASE に載っている。

文書 行末の平均のずれ 1pt 以内に収まる行
調査票(110 行) 9.01pt → 2.50pt 5 → 68
告知書(141 行) 3.71pt → 2.54pt 5 → 83

まだ届いていない所も、そのまま書いておく。*配っているのはエンジンだけで、画面のアプリはまだ配っていない*。表の列の幅の取り方で折り返しが一字ずれる文書がある。表計算の頁割りが原本と合わない帳票がある。そして AsciiDoc の読み書きは、まだ配っていない。前の節の決めは方向であって、この道具でいま全部できるわけではない。

文書が住める場所は三つある ── Claude Docs をどう置くか

2026-09-16 に、Claude Docs がベータで出た。会話の中で文書を作り、人が直接編集し、コメントを付け合い、共有するところまでが Claude の中で完結する。 2026-09-20 に確かめた時点で、Pro・Max・Team・Enterprise で使える。

これは便利だ。道具を入れる必要がない。下書きを作って、直して、相談する場所としては、いまある中でいちばん手が少ない。

同時に、構造は Microsoft 365 と同じである。

  • 文書の実体は claude.ai の中にある。外から取りに行けない。読めるのは Claude の道具からだけだ
  • 共有リンクを開くには、相手にも Claude のアカウントが要る
  • Team と Enterprise の文書は、まだ組織の外へ共有できない
  • 顧客管理の暗号鍵、ゼロデータ保持、HIPAA 対応の構成を使う組織では、まだ使えない

違う点が一つある。出口がはっきりあることだ。Word、PDF、Markdown、Google Docs に書き出せる。Markdown まで出せるということは、原稿を文字で手元に落とせるということだ。

だから置き方が決まる。Claude Docs は、原稿を作って回す場所として使う。確定した原稿は Markdown で落とし、adoc に直して git に入れる。そうすれば、前の節の決めがそのまま効く。中身は手元に残り、Claude Docs は入口と出口を通過させる道具になる。

費用の比べ方も、ここではっきりさせておく。比べる相手は無料の道具ではない。 いま業者に払っている額だ。公開する Web の原稿を制作会社に頼んでいるなら、その一件の費用と比べる。人数分のライセンスを毎月払っているなら、その総額と比べる。2026-09-20 時点で Claude Pro は月 20 ドルである。

文書が住める場所は三つに増えた。どれを選ぶかではない。原稿を文字で持てば、三つとも通過させる道具になる。

なぜ別の保管アプリを足さないのか

文書というと Nextcloud のような OneDrive 代替を丸ごと立てたくなる。だが Nextcloud は PHP の重厚なモノリスで、別のユーザ体系も別のデータベースも抱え込む。この自立編が選んできた単一バイナリの軽さとは、逆を向いている。

2-04 で、認証を持つ PocketBase をもう立てた。文書の置き場は、それを門番にして、あとはファイルで足りる。

  • 実体 ── ファイルそのもの。重い保管アプリは要らない
  • 認証 ── 2-04 の門番がそのまま効く。別ログインを作らない
  • 権限・共有 ── 手元の構造化ストアが持ち、門番が身元を確かめる

実体はファイル ── 認証は門番、権限は構造化ストア

文書の実体は、ただのファイルとして自分のストレージに置く。レコードに埋め込まない。.adoc も .docx も .xlsx もファイルのまま持つ。そのほうが、後で機械 (Polars・AI)がそのまま読める。

置き場の第一の選択は、権限をどこに持つかだ。

  • 構造化ストア(推奨) ── すでに PostgreSQL を立てているなら、アクセス制御もそこに置く。門番しか無い小規模なら、門番の SQLite で足りる。問い合わせられ、トランザクションが効き、pg_dump で確実に残る
  • xattr(依存最小) ── 別ストアを足したくないなら、ファイルの拡張属性に貼る。ただし xattr は cp・rsync・tar・バックアップで静かに落ちる。複製と保存の経路で、属性が残ることを必ず確かめる
-- 構造化ストアにアクセス制御を持つ ── 問い合わせられ、消えない
-- doc_acl(doc_id, subject, perm)、subject は 'alice' か 'team:sales'
SELECT doc_id FROM doc_acl WHERE subject IN ('alice', 'team:sales') AND perm >= 'r';

権限のためだけに重い別アプリは要らない。門番が身元を、構造化ストアが権限を持つ。

既存の文書を移す

OneDrive・SharePoint に積まれた文書は、形式を変えずに運べる。

# rclone で吸い出し、自分のストレージへ並べる
rclone copy onedrive:Documents ./inbox --progress
# inbox/ の各ファイルの権限を記録する(構造化ストアへ、スクリプト一回)

移行は段階的でよい。並行で動かし、移り終えてから旧ストレージを解約する(2-10)。

これから書く物は、最初から .adoc で書く。これまでの物を全部変換する必要はない。新しい原稿から文字にしていけば、置き場は時間とともに入れ替わる。

社外とやり取りする ── 出口で渡す

取引先との共有に、専用の共有基盤は要らない。社外に渡すものは出口から出す。元ファイルではなく、.docx か PDF に変換して、メール(2-07)で送る。受け取りも同じで、届いたファイルは入口で開いてから、手元に入れる。

社外の人に、門番のアカウントは作らない。共同で編集までしたい相手はまれで、たいていは版のやり取りで足りる。送って、直って、返る。紙の時代から、ずっとそうだったように。

人は編集の道具、機械は Polars

ここで 2-03 とつながる。人は編集の道具で入れて読み、機械は Polars と DuckDB で裏のデータを捌く。同じ .xlsx を、人は編集の道具として、機械は入力として扱う。

  • 人が作る集計表・申請書・提案書 ── aiseed office で開いて、しまう
  • 数百万行の突き合わせ・全社集計 ── Polars が .xlsx を読み、PostgreSQL に書く

表計算は人の道具に戻り、重い処理は機械の道具へ移る。

参考実装 ── kura

この構成を実際に組んだのが、公開リポジトリ kura (aiseed-dev/workspace)だ。中小の業務利用を狙った、Microsoft 365 / Google Workspace の自前代替である。

  • 認証 ── PocketBase(差し替え可能なトークン検証と短期キャッシュ)
  • 権限 ── 依存最小を採り、ファイルの xattr に持つ
  • 実体 ── ファイルそのもの
  • 編集 ── 編集エンジンを JWT とコールバックで重ねる(FastAPI + Flet)

確かめ方

この章は、次の五つができていれば済みだ。

  1. 自分の .docx の様式を aiseed office で開いて、Word と同じ頁数で刷れる
  2. .adoc の原稿を git に入れて、直した行だけが差分に出る
  3. 同じ原稿から PDF と .docx の両方が出る
  4. 門番でログインした人が、自分に権限のある文書だけ一覧に見える
  5. cp -a と rsync -X で複製しても、権限が消えていない(xattr を使う場合)
pip install officework
git diff 原稿/2026-09-事業報告.adoc     # 直した行だけが出る
getfattr -d 文書.docx                    # xattr を使う場合だけ

人が持つ物

人が渡す値

  • 文書の置き場のパス
  • 編集エンジンと門番で共有する署名鍵
  • 誰がどの文書を開けるかの決め(部署、役割)

AI が「やる前に言う」操作

  • 既存の文書を一括で変換する、または移動する
  • アクセス制御の表を書き替える
  • 社外へファイルを送る

確かめた版と日付

  • aiseed office(officework)エンジン 0.5.0。pip install officework。 2026-09-04 公開、2026-09-20 に PyPI で確認
  • 画面のアプリと AsciiDoc の読み書きは、2026-09-20 時点でまだ配っていない
  • Claude Docs は 2026-09-16 にベータ公開。Pro・Max・Team・Enterprise で使える。 2026-09-20 に確認
  • 権限の置き場は PostgreSQL または門番の SQLite
  • 手順を書いたのは 2026-09-20
  • 版が上がっていたら、AI に公式の手順を確かめさせてから進める

まとめ

置き場を選ぶのではなく、原稿の持ち方を決める。

  • 原稿は adoc の文字 ── git で差分が取れる。AI がそのまま読み書きする
  • git に入れるのは原稿だけ ── デザインは別の置き場。履歴に中身の差分だけが残る
  • 様式は aiseed office ── ONLYOFFICE が日本語の様式に合わないから作った。エンジンは 0.5.0。画面のアプリと adoc の読み書きはまだ
  • Claude Docs は通過させる ── 下書きと共同編集は速い。確定した原稿は Markdown で落として手元に入れる
  • 実体はファイル ── 認証は門番、権限は構造化ストア。重い保管アプリを足さない
  • 比べる相手は無料ではない ── いま業者に払っている額と比べる
