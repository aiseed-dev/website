Drop WordPress;
publish with no server.

Drop dynamic WordPress and publish a static site with no server — build, verify, deploy as separate steps

2026.07.14 🌐 日本語

A company website can be static. The previous chapter put meetings and booking on your own side. Here we publish the web that faces outward. Take the static site you built with AI in the parent series' Chapter 6, drop dynamic WordPress, and put the baked HTML on Cloudflare Pages. Hold no server.

WordPress can go

WordPress is a mass of dynamic server, database, and plugins. The burden of updates, maintenance, and security never stops. A company site's contents rarely change. So static is enough. Static needs no server and no DB, and has almost no surface to attack. Publish the html/ you built in the parent series' Chapter 6, as-is.

Put it on Cloudflare Pages, and hold no server

Put the HTML on Cloudflare Pages. No server is needed. Upload the files and they are served from a global CDN, with HTTPS added automatically.

Leave delivery and defense to Cloudflare, and keep the source and the build in your own hands. The published HTML holds no secrets, so this part is safe to hand off.

Separate build, verify, and deploy

Publish in separate steps. Do not combine them.

# 1. Build — make html/
python tools/build.py
# 2. Verify — open the html/ you made and look at it
python -m http.server --directory html 8000
# 3. To a preview — check on the real platform before production
python tools/deploy_pages.py html --branch preview
# 4. Once verified, to production
python tools/deploy_pages.py html --branch main

Do not use auto-rebuild, and do not use a command that combines "build and deploy." The point is to *keep the HTML you verified identical to the HTML that goes live* (the detailed procedure lives in an internal manual). Uploading needs no npm and no Node — one script hitting Cloudflare's API is enough. That script is published as cf-publish (aiseed-dev/cf-publish): one line, cf-publish html --project <name>, and only the files that changed go up.

Connect the domain as a custom domain

Add your own domain in Cloudflare Pages as a custom domain. If your DNS is on Cloudflare, the A record that used to point at your server switches to Pages automatically, and the certificate is added automatically.

Leave mail (MX, SPF) untouched. You are only changing where the web is served. If you are unsure, keep the old server running and verify on the preview before pointing the production domain.

Wire only the moving parts

Wire the backend only for the moving parts, such as a contact form. The target is your own API behind the gate of 2-04. Auth is at the gate, storage is in the 2-03 DB, and notification goes through the 2-07 mail. Most of the site is static, and only what needs to move, moves.

Internal tools stay behind the gate

The public site is borrowed on Cloudflare Pages. But the internal tools stood up in this part — gate, documents, code, mail, meetings — are different. They carry secrets and raw data, so they stay behind the gate, your own reverse proxy.

  • The public site (static, no secrets) — borrowed on Cloudflare Pages
  • The internal tools (auth, business data) — on your own side, behind the gate

Borrow the window, hold the vault. Decide separately what to borrow and what to keep.

A borrowed window can be swapped at any time. The public site's substance is a pile of static files and the sources in your own hands. Nothing is deposited with Cloudflare. Put the same files on another host tomorrow, and the move is complete. The window is borrowed, but the exit is always open.

How to check you are done

This chapter is done when these five hold.

  1. The published site opens on your own domain and the browser shows the lock mark
  2. The page you looked at on port 8000 locally and the production page look the same
  3. Before production, the same page opens and can be checked at the preview URL
  4. Sending the contact form produces a notification in the 2-07 mail and a row in the 2-03 DB
  5. Mail still arrives as before, because MX was never touched
curl -sI https://example.com | head -1        # the published page answers
curl -sI https://example.com | grep -i server # delivery has moved to Cloudflare

What the human holds

Values the human supplies

  • The domain name to publish on
  • The Cloudflare account and its API token
  • The Pages project name (the value passed to --project <name>)
  • The URL of your own API that the contact form posts to
  • The address that receives contact notifications (the 2-07 mail)

Actions the AI states before performing

  • Deploying to the production branch (--branch main)
  • Adding the custom domain and switching the A record to Pages
  • Shutting down the old server
  • Changing the MX or SPF records in DNS (this chapter does not touch them)

Versions checked, and when

  • Cloudflare Pages, cf-publish (aiseed-dev/cf-publish), Python's http.server
  • This procedure was written on 2026-07-14
  • If a version has moved, have the AI confirm the official procedure before proceeding

Summary

Drop WordPress, and publish with no server.

  • Drop WordPress — shed the maintenance burden of a dynamic server, DB, and plugins
  • Cloudflare Pages — publish with no server; borrow CDN and automatic HTTPS
  • Separate build, verify, deploy — ship exactly what you verified
  • The domain switches automatically — a custom domain points the A record at Pages; leave mail untouched
  • Borrow the window, hold the vault — internal tools stay behind the gate
