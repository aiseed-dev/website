Put the mailbox
on your own side.

Outside Exchange and Outlook — receive it yourself, send it honestly

2026.07.09 🌐 日本語

Mail is the record of the business itself. Correspondence, contracts, history — all of it piles up there. By now the foundation, the gate, the code, and the documents are on your own side. This chapter takes back the inbox those records flow into every day. But mail is also a domain to be honest about. *Receiving is easy; sending — deliverability — is hard.* Stand it up with that line drawn clearly.

Take control of the inbox back to your own side

  • Control of the record — retention, search, and export of past mail by your own rules
  • Step off per-seat billing — the monthly bill does not stack with mailbox count
  • One with the gate — align accounts with the 2-04 authentication

Stand up Stalwart on one machine

The mail server is Stalwart. A Rust single server carries SMTP, IMAP, JMAP, spam defense, and DKIM signing. It is a replacement for Exchange. Storage can be pointed at the PostgreSQL from 2-03. The machine it stands up on is the one handed to the AI in 2-02.

# compose.yaml — stand up a single mail server
services:
  mail:
    image: stalwartlabs/mail-server:latest
    volumes: ["./stalwart:/opt/stalwart-mail"]
    ports: ["25:25", "587:587", "465:465", "993:993", "8080:8080"]
    restart: always

In the admin UI (:8080), create the domain and the mailboxes. No code is written.

Get the DNS right — MX, SPF, DKIM, DMARC

With mail, the DNS is the real body of the work, more than the server. Set these four correctly.

example.com.      MX    10 mail.example.com.
example.com.      TXT   "v=spf1 mx -all"
default._domainkey.example.com.  TXT  "v=DKIM1; k=rsa; p=...(generated by Stalwart)"
_dmarc.example.com.  TXT  "v=DMARC1; p=quarantine; rua=mailto:dmarc@example.com"

Set the reverse record (PTR) for the server's IP as well. Miss this, and the mail you send does not reach anyone.

Borrow outbound deliverability from a relay

Direct sending from a self-hosted server is at the mercy of IP reputation, blocklists, and each provider's judgment. Sometimes it does not arrive. This is not about OSS being inferior. It is the reality of how mail works.

So the realistic design is this.

  • Receiving, storage, search — owned by your Stalwart, and this is the real body of control
  • Outbound sending — go through an authenticated SMTP relay, a send-only service

The relay is a thin layer that borrows only sending deliverability. The mailbox itself stays on your side. Separate where you hold control from where you borrow deliverability. That is the honest, durable way.

"All in-house" is not always the right answer for mail. The inbox on your side, the sending deliverability borrowed — stand it up with the line drawn.

Read and write with Thunderbird

Reading and writing work with any client that speaks IMAP / JMAP. Thunderbird is free and runs the same on Windows, Mac, and Linux. Phones connect with the stock mail app over JMAP / IMAP.

Migrate from Microsoft 365 in parallel

Existing mail moves with imapsync, which syncs one IMAP store wholesale into another.

imapsync --host1 outlook.office365.com --user1 you@old \
         --host2 mail.example.com      --user2 you@new

There is no need to cut over at once. Receive on both for a while, set forwarding, and run in parallel. Point the MX at Stalwart once things have settled (2-10).

Migration is the same from Gmail. imapsync connects IMAP to IMAP, and it does not care whether the far side is Microsoft or Google.

Retention and safety are a few lines of rules

Mail retention needs no dedicated archive product. All the mail already sits in the 2-03 PostgreSQL, and it is already inside the 2-01 rule "protect the data and the spec." How many years to keep is one line in the business-rules Markdown. That is the entire retention spec.

The safety side is one line too. Never open executable attachments. Spam is handled by Stalwart's built-in filter. For a suspicious mail, have the AI read the body before any attachment is opened, as input to your judgment.

How to check you are done

This chapter is done when these five hold.

  1. A mail sent from an outside address, such as Gmail, to your own domain can be read in Thunderbird
  2. A mail sent from Thunderbird to an outside address lands in that person's inbox
  3. You can log in to the admin UI (:8080) and see the domain and mailboxes you created
  4. Queried from outside, all five records answer: MX, SPF, DKIM, DMARC, PTR
  5. Past mail carried over by imapsync is visible inside Thunderbird
dig +short MX example.com                      # the MX answers
dig +short TXT default._domainkey.example.com  # the DKIM key answers
dig +short -x <the server's IP>                # the reverse record (PTR) answers

What the human holds

Values the human supplies

  • The mail domain name and the mail server's hostname
  • The server's fixed IP, and whoever sets the reverse record (PTR) for it
  • The name and password of the first administrator in the admin UI
  • The account and credentials of the SMTP relay used for sending
  • The account and password on the old server, such as Microsoft 365, handed to imapsync
  • How many years mail is kept

Actions the AI states before performing

  • Changing a DNS record, above all switching the MX to Stalwart
  • Sending mail to an outside address
  • Running imapsync against the old server
  • Deleting a mailbox

Versions checked, and when

  • Stalwart (stalwartlabs/mail-server:latest), PostgreSQL, Thunderbird, imapsync
  • This procedure was written on 2026-07-09
  • If a version has moved, have the AI confirm the official procedure before proceeding

Summary

The inbox, on your own side.

  • Stalwart — SMTP, IMAP, JMAP, spam defense, DKIM in one server (on the 2-03 PostgreSQL)
  • DNS (MX, SPF, DKIM, DMARC, PTR) — the real body of mail is here
  • Lean on a relay for sending — inbox yours, deliverability borrowed, line drawn
  • Thunderbird — a free client, identical across OSes
  • imapsync — migrate from Microsoft 365 in parallel, point the MX last
