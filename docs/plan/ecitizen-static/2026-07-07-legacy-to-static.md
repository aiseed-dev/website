# 15年運営した動的サイトを「git に凍結」し、同じデータでスマホアプリまで作った話 (技術編)

*(ブログ記事ドラフト — 2026-07-07 の作業記録。
産業編「[プラットフォームの重力が消えていく](2026-07-07-platform-gravity.md)」に続く)*

統計メモ帳 (ecitizen.jp) は 2011 年から ASP.NET で運営してきた統計サイトです。
これを「静的サイト + Python によるビルド時生成」に移行するプロジェクトが
大詰めを迎え、この数日でやったことを記録しておきます。
どれも従来のWeb開発の常識からは外れたやり方ですが、結果はむしろ堅牢になりました。

## やったこと

### 1. データベースの中身を git リポジトリに移設した

旧サイトの一次データ (App_Data 203MB) のうち、実際に使っている分だけ —
1,741 市町村 × 35 年分の国勢調査・将来推計など 125MB・11,058 ファイル —
を新リポジトリの `data/legacy/` にコピーして、**そのまま git にコミット**しました。

「データを git に入れるな」は常識ですが、これは逆です。
1980〜2015 年の国勢調査は**もう二度と変わらない確定データ**で、
しかも加工済みのこの形では再取得できない。つまりソースコードと同じ
「凍結すべき一次資料」です。git に入れたことで:

- clone するだけで完全なビルド環境になる (DB サーバーも API キーも不要)
- データの変更履歴が diff で追える
- 消失リスクが GitHub との多重化で消える

移設のコード変更は、レイアウトを旧構造のまま鏡写しにしたので
**参照元パスの定数 2 行だけ**でした。

### 2. 「同じものが作れる」ことを機械的に証明した

移設ミスは目視では見つけられないので、検証は全数比較にしました。

- 取得層: 中間データ **3,745 ファイルの md5 が移設前と完全一致**
- 描画層: サイト全体をフルビルドして**総ファイル数 12,973 が一致**、
  コピーされる画像はバイト単位で一致

これで旧リポジトリ (15年分の ASP.NET) は `rm -rf` できる状態になりました。
「消せる」と判断する根拠がハッシュ値というのが、いかにも静的サイトらしい。

### 3. 同じデータスナップショットから、スマホアプリも作った

サイトの静的化と並行して、**統計APIエクスプローラ**というアプリを
2 種類作りました。e-Stat (政府統計の総合窓口) の約 24 万の統計表カタログを、
統計局のサイトより速く快適に探せることを目指したものです。

- **Flet 版** (Python) — Android・Chromebook の Linux 環境・デスクトップ向け。
  Python なので思いついたコードをすぐ足せる実験場
- **Flutter 版** — Web・PC・スマホのマルチプラットフォーム配布の本命
  (アプリID: dev.aiseed.ecitizen)

常識外なのはアプリの中身です。**アプリは e-Stat の API を一切呼びません。**
カタログはローカルバッチが取得して JSON スナップショットにし、
サイトと同じ静的配信に載せる。アプリはそれを読むだけ。だから:

- 統計局のサーバーに負荷をかけない (API キーもアプリに入らない)
- オフラインでも動く。表示は常に一瞬
- サイトとアプリが**同一のデータ**を見る (齟齬が起きようがない)

グラフも同じ思想で、ビルド時に matplotlib が SVG を生成し、
アプリはそれを表示するだけ。実行時に描画コードは走りません。
(この過程で flutter_svg が日本語フォント指定を解釈できない問題を見つけ、
派生パッケージ flutter-svg-cjk-friendly を作って解決しました。
欧米では起きない問題は、本家に要望を残して派生で解く。)

そもそも今までは、**アプリよりも Web の方が圧倒的に作りやすかった**。
だから何でも Web になった — フレームワークの学習、プラットフォームごとの
作法、ストア配布。個人がアプリに手を出すには手間が違いすぎました。
でも AI と組んで作ると、**Web もアプリも同じ手間**です。実際、Flet 版と
Flutter 版は静的サイトの合間に生まれました。

むしろ画面数がある程度多くなると、**Web ですら Flutter の方が作りやすい**。
画面が増えても部品 (Widget) の組み合わせとルーティングの追加だけで、
HTML/CSS/JS を画面ごとに書くより速い。統計APIエクスプローラの Web 版も
Flutter Web でビルドして静的サイトの /Statdb/ に載せています —
一つのコードベースが Web・PC・スマホの全部になる。

これは Chromebook 対策としても効きます。教育現場に一番普及している
Chromebook は「ブラウザ・Android アプリ・Linux アプリ」の3つの顔を
持ちますが、管理された端末ではインストールが制限されがちです。
この構成なら Web 版がインストール不要で動き、許可があれば Android 版・
Linux 版も同じコードベースで提供できる。統計教材として使うときは、
設定で教科書体を選べるようにもしてあります。

セキュリティの面でも、ブラウザより Android / Linux アプリの方が
攻撃されにくい。ブラウザは「あらゆるサイトのコードを実行する」
汎用実行環境で、フィッシング・XSS・悪意あるスクリプトと隣り合わせです。
このアプリは自分の UI しか描画せず、外部のコードを一切実行しない。
参照先も自サイトの静的 JSON に固定されていて、その上 OS の
アプリサンドボックス (Android / Crostini の VM) に包まれています。
サーバー側の公開面をゼロにした後に残るのは利用者側の面ですが、
そこもアプリ配布なら狭くできる、ということです。

面白いのは、Flutter だと**静的サイトなのに動的なテンプレートが使える**
ことです。人口ページ (約13,000ファイル) はビルド時に Jinja2 で全ページを
生成しました。しかし統計カタログは約 24 万表 — ホスティングのファイル数
上限 (Cloudflare Pages は 2 万) を超えていて、事前生成では作れません。
Flutter なら「テンプレートの実行」をクライアント側に移せる。配信するのは
静的な JSON だけで、画面はユーザーの手元で組み立てられる。
サーバーで何も実行しない、という原則はそのままに、
事前生成の限界を超えられます。
作りやすさでプラットフォームを選ぶ時代が終わり、「オフラインで動く」
「ホーム画面にある」といった本来の価値で Web かアプリかを
選べるようになった、ということです。

### 4. ライセンスを三層に分けた

公開にあたって、リポジトリの中身は性質が違う三つに分かれることに
気づきました。一枚のライセンスでは覆えません。

| 対象 | ライセンス |
|------|-----------|
| プログラム (ビルドスクリプト・テンプレート・アプリ) | AGPL-3.0-or-later |
| 加工済み統計データ (`data/legacy/` 等) | CC BY 4.0 (© aiseed.dev) + 元データの出典明記 |
| フォント (モリサワ BIZ UD、ビルド用) | SIL OFL 1.1 |

データを「コードのおまけ」にせず、独立した著作物として CC BY を明示したのは、
データこそがこのサイトの本体だからです。

### 5. 公開して大丈夫かを「全履歴の機械走査」で確認した

リポジトリを公開した後、全コミットの全ファイルに対して
API キー・トークン・アカウント ID のパターン検索をかけました。
結果、ヒットは全てプレースホルダ (`G-XXXXXXXXXX` など) のみ。
秘匿情報の混入ゼロを数分で確認できました。

「公開前レビュー」を人間の記憶と目視に頼らず、履歴を含めて
機械的に走査する — これも今までの常識にはなかった安心感です。

ついでに、e-Stat API の利用規約が求める注記がフッターから漏れていたことも
この点検で発見して修正しました。認証キー (appId) も、事故が構造的に
起きないようリポジトリの外 (`~/.config/`) に移しました。

### 6. フォントは「配らない」と決めた

日本語 Web フォントは 1 書体で数 MB あります。当初は BIZ UD ゴシックの
woff2 (計 9.5MB) を自己ホスト配信していましたが、全部やめました。
サイトもアプリも**フォントを一切同梱・配信しません**。

- **Web**: システムフォント。BIZ UD は Windows に標準搭載されており、
  Mac はヒラギノ、Linux/Android は Noto にフォールバック
- **アプリ**: フォント名の指定だけ持つ。「あれば使い、無ければ OS 既定」。
  設定画面で BIZ UDゴシック / 教科書体 (Klee One) / OS 標準を選択でき、
  インストール済みフォントの名前を直接指定もできる
- **良いフォントは本人が入れる**: Windows は最初から入っている。
  他の OS は Google Fonts や apt (`fonts-morisawa-bizud-gothic`、
  `fonts-klee`)、モリサワ Fonts のフリープランで無料インストールできる。
  その入手方法をアプリの設定画面に書いておく

やっと日本語フォントが「ユーザーの環境に良いものがある」時代になったので、
配信で押し付けるのではなく、環境にあるものを最大限活かす方に振りました。
転送量はゼロになり、フォントの品質はユーザーの環境に応じて上がっていきます。
ついでにダークモード切替 (ライト/ダーク/OS 追従) も両アプリに付けました。

なおリポジトリに TTF は残っていますが、ビルド時の matplotlib の
レイアウト計算専用と、描画回帰テスト専用で、配布物には含まれません。

## なぜこのやり方が成立するのか

三つの設計原則に集約されます。

1. **確定したデータは実行時に取得しない** — 外部 API を呼ぶのは
   ローカルバッチだけ。成果物はスナップショットとして git に凍結し、
   サイトもアプリも実行時には外部に何も依存しない
2. **ランタイムに汎用 AI を入れない** — AI は開発時の協働相手。
   出力はコード・テスト・文書として git に凍結され、レビューも再現もできる
3. **出口コストをゼロに保つ** — 静的ファイルと Python スクリプトだけなので、
   ホスティングも移行先も選び放題。旧システムはハッシュ一致を確認して消すだけ

そして個人開発なら、**サーバーは最小限**であるほどいい。
サイバー攻撃対策としてもです。

- 公開面が桁違いに小さい。動的サイトは、開放ポート・リクエストごとに
  実行されるコード・DB への経路・フォームの受け口と、外部に晒すものだらけ
  でした。今、外に見えているのは CDN が「ファイルをそのまま返す」機能
  だけ。SQL インジェクションもリモートコード実行も、
  **攻撃する対象そのものが存在しない**
- 残る攻撃面は CDN アカウントと DNS の管理、ビルド時の依存パッケージ、
  手元のビルドマシンくらい。「24時間公開の面」から
  「ローカルとアカウント管理の面」へ、守る場所が移動した
- 動的サイトは「動いているだけ」でリスクが増えていく。実際、旧サイトの
  ASP.NET Core 2.2 はとっくにサポート終了で、セキュリティパッチはもう
  来ません。個人がフレームワークの更新に追従し続けるのは現実的でない
- 認証情報は本番に置かない。e-Stat の API キーはローカルの
  `~/.config/` にだけあり、配信サーバーにもアプリにも入っていない
- 監視・侵入検知・パッチ適用といった「運用」が丸ごと消える。
  一人で作って一人で守るなら、守るものを減らすのが一番確実

動的サイト全盛の 2011 年には、統計サイトには DB と API サーバーが
「当然」必要でした。15 年経ってみると、確定した統計を配るのに
実行時に動くものは何一つ要らなかった、というのが結論です。
そしてその同じスナップショットが、そのままスマホアプリのデータ基盤に
なりました。サーバーを持たないことは、制約ではなく資産でした。

この一連の作業は、AI (Claude) との協働で行いました。移行プロジェクト全体は
従来のやり方なら数ヶ月がかりでも終わらなかったはずですが、方針の判断
(何を凍結するか、ライセンスをどう分けるか、フォントを配るか配らないか) は
全て人間側にあります。手が速くなった分、判断に時間を使える。
それが一番の変化かもしれません。
